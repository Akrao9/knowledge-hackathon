# Submission notes

The submission keeps every snapshot and answers from the latest one on or before the requested date. Each snapshot is the whole site as of its date, so an "as of" question reads that snapshot alone. When no date is passed but the question names one ("as of May 2026", "as of June 9, 2026"), that date is used in the same way, with a month meaning its last day, so a date before the first snapshot gets "I don't know". Questions go through three stages in order: a few prose facts, the rate-table index, then section search.

## Rate-table index (`rate_tables.py`)

Rates live in tables, so every table row with a percentage becomes a fact record. A record holds the page, the headings and captions above the table (the rate sheet labels products with plain caption lines such as "Certificates / Special Certificates"), the row's label cells, and each percentage with its type: APY, dividend rate, APR or interest rate. A unit printed in the cell beats the column header, because some pages reuse another table's header. Rows also carry the qualifiers they price: term, model-year range and balance or loan-amount range. Tables whose "Rates are effective" date is after the snapshot date are skipped.

A rate question is matched to rows by the rarity of the words they share, after synonyms (CD and certificate, car and auto, mortgage and home loan). The question's term, model year and amount must fall inside a row's tier; where several "or less" tiers cover one amount, the narrowest applies. Rows for non-default variants (business, jumbo, refinance, IRA, introductory rates) are dropped unless the question names them or asks for a list; "non-jumbo" or "not the balance transfer rate" excludes the variant instead. Dates in the question ("as of September 28, 2026") are removed before model years are read. If a question names a variant no matching row carries (ARM, FHA, construction, student, a jumbo term that doesn't exist), or its term or tier isn't published, the answer is an honest "isn't listed". A product word in the question must appear in a row's own caption or label, so certificate rows on the savings page don't answer a savings question. A question with two or more words no rate table uses ("What statement enrollment is required to earn dividends on Bright Savings?", "How many points do I earn per dollar?") that doesn't ask for a rate figure (rate, APR, APY, percent) is about something else that rate words only touch, so it goes to search. When the question has a word the matching rows don't carry ("kids savings", "signature loan", "personal line of credit") and those rows span several products or are all a variant it didn't ask for, the index doesn't guess: the question goes to search, which won't quote a rate table again and, without an API key, only quotes a passage that names that word.

What's current is decided by one page-trust rule: the rate sheets and product pages outrank landing pages, which outrank calculators, articles, newsroom posts and PDFs. Low-trust pages never supply an answer. Between equally trusted pages, the newer effective date wins, then the central rate sheet. When several pages publish the same tier, the answer uses the winner and notes that pages disagree. Rows count as the same product only if they share a caption on one page, or are each other's closest caption match across pages, so two cards with the same "Variable Interest Rate" label stay separate.

The same rule produces the conflict report. Rows on different pages that price the same tier of the same product (same label, term and ranges, matched by caption as above) with different values are reported once, with the winner as the resolution and the reason. Each tier is reported from the newest snapshot where it disagrees, and the APY or APR conflict stands in for the same row's dividend or interest-rate conflict.

## Prose facts and search

`snapshot_facts.py` answers what tables can't: the operating branch count from the latest dated press release (kept apart from projected openings; the site publishes only the total, so a count of some branches, such as those open on Saturday, with a drive-up or in one city, gets "I don't know"), membership eligibility from the Join page and the charter-area states, and whether a savings product pays a quoted percentage. It also reports conflicts between branch counts and between charter-area lists.

Headings and tables are found with `markdown-it-py` (`markdown_blocks.py`), so lines inside code blocks are never read as either. A question asking for a member's own balance ("What is the current balance in my checking account?") or for a decision about the member ("What APR would I be approved for?", "Will I qualify?", or an approval for a stated credit score) gets "I don't know", since no public page can answer it; questions about how to check a balance or what score a loan requires are answered as usual. Everything else uses a section index over Markdown headings, titles, URLs and body text, with special handling for branch hours, branch addresses and same-page links. Words that only frame a question ("use", "have", "need") are ignored. A plural word in a question also searches its singular at half weight ("students" finds "Student Loans", "lobbies" finds "Lobby"), while pages keep their own words. A question asking for a number to call, or for an extension to dial or reach someone, searches only sections that contain a phone number (a browser or scholarship extension keeps ordinary search), and one asking when something is open ("What time do lobbies open?", "When are lobbies open?") searches only sections with a weekly schedule; the schedule then stands in for "open", "close" and "what time", so it needs just one more question word, such as the service or the place. Teasers for other articles ("Handpicked for You" blocks, "Keep reading" blurbs, card titles linking to another page) are left out of the index, and passages that are only images or a list of links are never quoted. Articles, press releases and calculators rank below product pages, business pages rank below personal ones unless the question says "business" (the default the rate tables use), and a page the site serves at two URLs takes one search slot, not two. Without an API key, the local fallback returns the passage whose shared words are rarest across the snapshot and abstains when word overlap is weak; an FAQ question line counts as the heading of the answer paragraph below it. When an hours, address or location question names a place ("the Mullan Avenue branch", "hours at Mullan Ave"), in any capitalization, a passage counts only if its text, headings or page title contain every word of that name, with street abbreviations such as Ave and St expanded. Named branch-hours answers require a published schedule for the requested service.

## API key

Set `OPENAI_API_KEY` to enable the paid GPT-6 Luna API for the search stage only. The request sends the question and the top eight sections from the selected snapshot, split into numbered passages (paragraphs and single table rows), plus the next eight sections by their two passages that share the rarest question words, so a section just below the cut can still answer without doubling the prompt. Luna replies with the numbers of the passages that answer it, so the reply is a few tokens long and every quote is the snapshot's own text; passages chosen from one section are quoted together in page order. The call goes through the official `openai` SDK with retries off; one that takes longer than 2.5 seconds or fails falls back to the local answer, and a question asked again in the same run gets the answer it got the first time. Rate questions never depend on the API, and neither do comparison questions ("Do all branches keep the same lobby hours?"): those show the top three distinct matching passages in rank order, so every run gives the same answer. `requirements.txt` installs two packages, `markdown-it-py` and `openai`; without a key, `openai` is installed but never called.
